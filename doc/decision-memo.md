# Content Loop: решение о системе контента

## Решение

Строить. Не как автономного «писателя», не как набор cron-задач и не как SaaS с первого дня. Строить как отдельную систему управления жизненным циклом контента с человеческим шлюзом перед публикацией.

Главная ценность находится не в генерации. Генерация уже товарная функция моделей. Защищаемая ценность возникает из пяти вещей:

1. точного знания, что, где, когда и в какой версии опубликовано;
2. сохранения источников, утверждений и правок человека;
3. адаптации одного замысла под разные каналы без смыслового расхождения;
4. надёжной публикации с идемпотентностью и аудитом;
5. рефлексии по фактической реакции аудитории, а не по впечатлению модели.

## Почему система нужна

Уже есть три разных редакционных продукта и минимум три класса каналов. Ручной процесс будет дублировать идеи, терять историю публикаций и смешивать тональность. Простая генерация по расписанию увеличит объём, но не качество и не управляемость.

Система оправдана, если выполняются три условия:

- публикуется не меньше 2–3 материалов в неделю суммарно;
- одна идея регулярно превращается в несколько канал-специфичных версий;
- обратная связь влияет на следующий контент-план.

Если фактический объём ниже, достаточно редакционного календаря и ручного использования модели.

## Что именно строится

Не «агент, который сам всё делает», а редакционный конвейер:

`idea → brief → evidence → canonical draft → channel variants → checks → human approval → publish → reconcile → metrics → reflection`

LLM разрешено:

- предлагать темы и углы;
- собирать черновик на основании разрешённых источников;
- делать версии под канал;
- проверять стиль, структуру, дубли и SEO;
- формировать гипотезы по результатам публикаций.

LLM не разрешено:

- самостоятельно публиковать неутверждённый материал;
- превращать гипотезу в факт;
- использовать реакцию аудитории как единственный критерий истины;
- хранить состояние только в истории диалога или векторной базе;
- напрямую писать в таблицы FamilyOS.

## Человек в контуре

Человек не просто «валидирует текст». Он остаётся владельцем утверждений и редакционного направления.

Для каждого материала нужны решения `approve`, `edit`, `reject`. Изменения человека сохраняются как diff и становятся главным обучающим сигналом для будущих брифов. LangGraph поддерживает сохранение состояния, прерывание workflow и продолжение после человеческого решения; это соответствует требуемой модели, но не заставляет выбирать LangGraph как окончательный runtime ([LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence), [human-in-the-loop](https://docs.langchain.com/oss/python/langchain/human-in-the-loop)).

Политика риска:

- визы, право, налоги, цены и инвестиционные утверждения — утверждение каждого материала;
- фактические статьи о недвижимости — утверждение до каждого канала;
- общие AI-заметки — пакетное утверждение допустимо после стабильного пилота;
- автопубликация — только для заранее определённых низкорисковых форматов.

## Варианты реализации

| Вариант | Скорость старта | Контроль | Повторное использование | Риск | Вердикт |
|---|---:|---:|---:|---:|---|
| Модуль внутри FamilyOS | высокая | высокий | низкое | сильная связность доменов | допустим только как временный MVP |
| Отдельный сервис + адаптер FamilyOS | средняя | высокий | высокое | дополнительная эксплуатация | **рекомендуется** |
| n8n как вся система | высокая | средний | среднее | логика и состояние расползаются по workflow | прототип и интеграционный слой |
| LangGraph/Temporal как ядро | средняя | высокий | высокое | избыточность до подтверждения процесса | следующий этап при сложных long-running workflow |
| SaaS сразу | низкая | средний | потенциально высокое | строится рынок до проверки собственной пользы | не делать сейчас |

n8n пригоден для быстрого соединения API, самостоятельного хостинга и повторного запуска execution; его продвинутые совместные и некоторые human-fallback возможности зависят от редакции лицензии ([n8n overview](https://docs.n8n.io/), [executions](https://docs.n8n.io/workflows/executions/all-executions/), [workflow sharing](https://docs.n8n.io/workflows/sharing/)). Temporal и LangGraph решают durable execution, но это инфраструктурный ответ, а не готовая модель контента ([Temporal](https://docs.temporal.io/), [LangGraph overview](https://docs.langchain.com/oss/python/langgraph/overview)).

## Рекомендованная форма продукта

Рабочее имя: **Content Loop**.

Развёртывание: отдельный сервис и БД рядом с FamilyOS в K3s. Первый UI может появиться внутри FamilyOS как экран редактора, но общается только с API Content Loop. Ядро не знает таблиц FamilyOS, Telegram или Facebook; оно знает возможности адаптера.

Состав:

- API и состояние workflow;
- редакционный календарь и очередь утверждения;
- model gateway;
- реестр источников и проверяемых утверждений;
- рендереры каналов;
- publisher adapters;
- collectors для метрик;
- structured reflection engine;
- audit log и idempotency keys.

## Каналы и ограничения

### Telegram

Bot API подходит для публикации в канал и событий реакций. Для получения `message_reaction` и агрегированных `message_reaction_count` бот должен быть администратором и явно подписаться на эти типы обновлений; агрегаты могут приходить с задержкой ([Telegram Bot API](https://core.telegram.org/bots/api)). Просмотры и полноценную аналитику нельзя считать гарантированным read-back интерфейсом Bot API. Поэтому в MVP основными сигналами будут реакции, комментарии связанной группы и переходы по собственным UTM/redirect-ссылкам.

### Facebook

Публикация должна работать только с Page, Page access token и разрешениями приложения. Это отдельный интеграционный проект с токенами, App Review/Business Verification и версионированием Graph API. Официальная коллекция Meta показывает работу с Page-токенами ([Meta Facebook API collection](https://www.postman.com/meta/facebook/folder/3nyjb4m/tokens)). Facebook не должен блокировать запуск MVP.

### FamilyOS API

FamilyOS — нестандартный канал, но обычный publisher adapter. В текущем роутере уже существуют отдельные admin CRUD API для:

- PattayaDom: `/api/v1/articles`;
- SoulArchitecture.Space: `/api/v1/soul/articles`;
- AI.SoulArc.Space: `/api/v1/soul/ai-notes`.

Они различаются схемами. Следовательно, нужен не один «FamilyOS post», а конфигурируемые mappings поверх общего контракта адаптера. Безопасный режим — сначала создать `is_published=false`, сохранить внешний ID, затем отдельным PATCH публиковать утверждённую версию.

## Open source и SaaS

Open source имеет смысл для ядра и SDK адаптеров. Не публикуются:

- редакционные профили проектов;
- секреты каналов;
- частные источники;
- исторические метрики;
- конкретные промпты, если они содержат внутреннюю стратегию.

SaaS становится рациональным после трёх доказательств:

1. система стабильно используется собственными проектами 8–12 недель;
2. подключён хотя бы один внешний проект без изменения ядра;
3. внешний пользователь готов платить за approval, provenance, adapters и analytics, а не за «генерацию AI-текстов».

## Критерий остановки

Проект закрывается или упрощается до набора workflow, если через 8 недель пилота:

- меньше 70% черновиков доходят до публикации;
- медианное ручное редактирование превышает 50% текста;
- подготовка материала не стала быстрее минимум на 30%;
- рефлексия не меняет темы, форматы или следующие брифы;
- журнал публикаций остаётся неполным.

## Конечная рекомендация

Сделать вертикальный срез `PattayaDom → FamilyOS draft → human approval → Telegram + FamilyOS publish → reaction/link metrics → reflection`. Не начинать с Facebook, универсального multi-agent harness, marketplace адаптеров или SaaS-биллинга.
